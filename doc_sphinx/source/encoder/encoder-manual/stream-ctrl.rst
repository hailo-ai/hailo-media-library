Stream Production
=================

After a successful initialization and an optional configuration step,
the encoder is ready to produce an HEVC-or H.264-compliant stream. There
are three separate phases for producing a stream:

1. **Starting the stream** by calling
   :ref:`VCEncStrmStart <VCEncStrmStart>`\ ()

2. **Encoding video frames** by calling
   :ref:`VCEncStrmEncode <VCEncStrmEncode>`\ ()

3. **Ending the stream** by calling :ref:`VCEncStrmEnd <VCEncStrmEnd>`\ ()

Starting the Stream
-------------------

A stream must be started by a call to
:ref:`VCEncStrmStart <VCEncStrmStart>`\ (). Video Parameter Set (VPS),
Sequence Parameter Set (SPS) and Picture Parameter Set (PPS) NAL units
are produced at this time. The user must provide an output buffer where
the stream header data will be written. The output buffer is specified
with a pointer to the buffer and the size of the buffer in bytes. If
successful, the call will return VCENC_OK and the size of the generated
stream in bytes. If NAL units are needed, then the buffer for sizes must
be specified when starting the stream.

Encoding Video Frames
---------------------

A video sequence can be encoded after a stream has been started. A video
sequence is encoded frame by frame by calling
:ref:`VCEncStrmEncode <VCEncStrmEncode>`\ (). The main inputs for this
function are an input buffer, which contains the video frame to be
encoded, and an output buffer where the generated stream will be
written.

The supported formats of the input video are planar YCbCr 4:2:0,
semiplanar YCbCr 4:2:0, interleaved YCbCr 4:2:2, planar I010, semiplanar
P010, planar YCbCr 4:2:0 10 bits packed, YCbCr 4:2:0 10 bits (Y0L2) and
RGB (565, 555, 444, 888 or 101010). The format in use has been selected
during the pre-processor configuration. Regardless of the input format
used the input frame buffers must be 128-bit aligned, linear and
hardware accessible. In other words, the addresses which are passed as
parameters to the :ref:`VCEncStrmEncode <VCEncStrmEncode>`\ () function,
are bus addresses and will be given to the hardware unmodified. These
addresses will be used by the hardware to read the input video frame.

The output buffer is used by the software to construct the final stream.
The pointer to the buffer will be passed to the
:ref:`VCEncStrmEncode <VCEncStrmEncode>`\ () encode function. The size of
the buffer must be correlated with the target bit rate and frame rate.
For example, when the target bit rate is 3 Mbps and the frame rate is 30
fps, the average frame size is 100 000 bits. Keep in mind that this is
an average value and single encoded frames can take many times more
space. In a typical case, a buffer size equal to the bitrate of the
stream is adequate. The maximum size of the encoded frame depends on the
input picture. If the encoder reaches the end of the output buffer, it
will discard the current frame and return VCENC_OUTPUT_BUFFER_OVERFLOW.
This is even more likely when the rate control is disabled. Even if the
current frame is lost, the encoding process can continue with a new
frame which will be INTRA coded to assure that any errors are not
propagated.

Another important parameter for every video frame is its time stamp.
This must be specified at every call to
:ref:`VCEncStrmEncode <VCEncStrmEncode>`\ (). The time stamp is relative
to the previous frame and it is specified as a time increment in ticks.
The duration of a tick is specified at the initialization according to
the frame rate numerator. The first encoded frame normally has a time
increment of zero. For fixed frame rate video, i.e. every frame has
equal duration, the time increment is equal to frame rate denominator.
For example, if the frame rate is set to 1000/33 the time scale is 1000
ticks and the relative time between each frame is 33 ticks. When the
frame has been successfully encoded,
:ref:`VCEncStrmEncode <VCEncStrmEncode>`\ () returns VCENC_FRAME_READY.

Each encoded frame can be divided into several slices. Slices help in
the error recovery of the erroneous streams and their role is to split
the frame data into smaller independent packages. The size of a slice is
specified in CTU rows.

The individual NAL unit sizes can also be known. The user must provide a
buffer where the sizes of all NAL units are returned. The encoder will
fill this buffer with the size of each unit in bytes. After the last
unit, a zero value is written to the size buffer. This information is
needed for separating each NAL unit from the byte stream for the case of
stream type of VCENC_NAL_UNIT_STREAM. A table of 516 bytes
(129*sizeof(u32)) is sufficient to fit sizes for the maximum number of
slices that can be generated by the encoder.

Ending the Stream
-----------------

A stream will be ended by a call to
:ref:`VCEncStrmEnd <VCEncStrmEnd>`\ (). If successful, the call will
return VCENC_OK. Stream end consists of a NAL unit of type
'End-of-Sequence'.

Interlaced Coding
=================

Interlaced video consists of fields where two fields (top and bottom)
comprise one video frame. Interlaced coding mode encodes top and bottom
fields of a frame separately. This improves the compression efficiency
of interlaced video content compared to normal progressive frame coding.

The input picture for interlaced coding is both fields interlaced into
one frame. When the interlaced frame input format is used, the same
frame is used as input for two consecutive encode calls and the
pre-processor switches between reading either top or bottom field.

Video Pre-processor Usage
=========================

The encoder includes the following pre-processing blocks:

1. 30-, 24-, 16-, 15- or 12-bit RGB to YCbCr 4:2:0 conversion

2. YCbYCr 4:2:2 to YCbCr 4:2:0 conversion

3. I010, P010, planar YCbCr 4:2:0 10 bits packed, Y0L2 to YCbCr 4:2:0
   conversion

4. Picture rotation

5. Picture cropping

By default, the encoder input is considered to be in planar YUV 4:2:0
format. Cropping and rotation are disabled. The pre-processor is
controlled by the :ref:`VCEncSetPreProcessing <VCEncSetPreProcessing>`\ ()
and :ref:`VCEncGetPreProcessing <VCEncGetPreProcessing>`\ () API functions.
It is recommended to retrieve the current values from the encoder first
and then do the necessary alterations.

Color Conversion
----------------

The color conversion block reads the input picture in 30-, 24-, 16-, 15-
or 12-bit RGB or interleaved YCbCr 4:2:2 format. The picture is
converted into planar YCbCr 4:2:0 format by color conversion,
sub-sampling the chrominance samples vertically and rearranging the
samples. The conversion is done during the configuration phase and it
will affect every encoded picture.

Picture Rotation
----------------

The rotation block rotates the picture 180 degrees or 90 degrees
clockwise or counter-clockwise. The rotation is configured during the
initialization phase and it will affect every encoded picture. The
figure :ref:`below <fig_encman_pic_rotation>` illustrates the resultant
encoded picture dimensions after rotating the input picture.

Picture Cropping
----------------

Picture cropping provides a way to read and encode a smaller selected
portion of a larger picture. The cropping is controlled by setting the
size of the input source picture and the top-left corner coordinates of
the encoded picture relative to the top-left corner of the input
picture.

The maximum size of the input source image is 8192x8192 pixels.
The maximum size of the output image is 4096x8192 pixels.

The figure :ref:`below <fig_relationship-between-input-and-encoded-image-sizes>`
illustrates the relationship between picture parameters. The conditions that
must be satisfied in order to enable the cropping block are as follows:

   *origWidth - xOffset - width ≥ 0*

   *origHeight - yOffset - height ≥ 0*

The input source picture horizontal stride (in pixels) must be multiple
of 16.

For example, when the input width is 630 pixels the horizontal stride
must be 640 pixels.

Offset of pixel *n* in the picture buffer:

.. math:: pixel\_ offset = \ \left( \frac{n}{width} \right)*\left( (width + 15)\ \&(\sim 15) \right) + (n\ \%\ width))
